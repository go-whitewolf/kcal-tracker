# CLAUDE.md

Контекст за Claude Code. Прочети този файл преди всяка промяна по проекта.

## Какво е това

Дневник за калориен баланс. Следи приети калории, изразходвани калории и тегло, и
калибрира изчисления разход спрямо реалната промяна на теглото.

Ползва се от няколко души — Мариус и двама-трима колеги — но **няма акаунти и няма общи
данни**. Всеки отваря един и същ адрес и получава собствен дневник в своя браузър, със свой
API ключ. Затова в кода не бива да остават ничии лични мерки като стойности по подразбиране:
профилът се попълва от първоначалния екран.

Отличителната функция: снимка на храна → Claude Vision оценява калориите → потребителят
потвърждава и записът влиза автоматично в дневника.

Интерфейсът е **изцяло на български**. Използва се на телефон, инсталиран като PWA.

## Архитектура

Статичен сайт без build step. Отваря се директно с `index.html` или се хоства на GitHub Pages.
Няма npm, няма bundler, няма зависимости. ES модули, заредени нативно от браузъра.

```
index.html              единственият HTML — трите изгледа са в него
css/app.css             всички стилове, дизайн токени в :root
js/
  util.js               дати, форматиране, escape, DOM хелпъри
  storage.js            persistence: window.storage → localStorage fallback, + wipe()
  state.js              единственият източник на истина (обектът S) + save()
  energy.js             BMR, TDEE, MET таблица, изчисления на баланса
  vision.js             камера, свиване на снимката, извикване на Claude API
  views/day.js          изглед "Днес"
  views/progress.js     изглед "Прогрес" — графика, таблица, калибрация
  views/settings.js     изглед "Профил" — данни, дефицит, API настройки
  views/welcome.js      първоначален екран при първо пускане
  main.js               рутиране между изгледите, инициализация
worker/index.js         Cloudflare Worker прокси (по избор, за скриване на ключа)
sw.js                   service worker, „мрежа преди кеш“ — виж правило 10
```

## Модел на данните

Един обект, сериализиран в един storage ключ (`kcal_tracker_v1`):

```js
{
  profile: { w, h, age, sex, mult, deficit, ready, api:{ mode, key, proxyUrl, model } },
  days: {
    "2026-09-07": {
      meals:    [{ name, kcal, prot, src }],      // src: "manual" | "photo"
      workouts: [{ name, type, min, km, kcal }],
      weight:   85.0 | null
    }
  }
}
```

Дните са речник по ISO дата, а не масив — така добавянето на ден не изисква сортиране
и няма дублирани записи. `day(key)` в `state.js` създава деня при първо докосване.

`profile.ready` е `false`, докато потребителят не мине през първоначалния екран. Архив
**без** това поле идва отпреди екрана и се брои за готов — `hydrate()` го маркира, за да не
пита втори път човек, който вече е попълнил профила си.

## Твърди правила

1. **UTF-8 навсякъде.** `<meta charset="UTF-8">` е първият таг в `<head>`. Всеки нов файл се
   записва в UTF-8 без BOM. Кирилицата се чупи безшумно, ако това се пропусне — проверявай
   с `file -i` при съмнение.
2. **API ключът никога не влиза в кода.** Въвежда се от потребителя в „Профил“ и стои в
   storage. Никакъв ключ в git, в примери, в коментари.
3. **Storage винаги минава през `storage.js`.** Не викай `localStorage` директно от друг модул —
   приложението трябва да работи и в среда, където съществува `window.storage`.
4. **Един storage ключ, едно записване.** Не разбивай данните на много ключове; при
   промяна се записва целият обект наведнъж чрез `save()`.
5. **Обратна съвместимост при четене.** Стари записи може да нямат нови полета. Всяка
   функция, която чете ден или профил, попълва липсващото със стойност по подразбиране,
   вместо да гърми. Не мигрирай данни разрушително.
6. **Без нови зависимости.** Ако нещо изисква npm пакет, първо предложи и попитай.
7. **Числата са оценки, не измервания.** Никъде в интерфейса не представяй изчислен
   разход като точен факт. Езикът е „около“, „приблизително“, „оценка“.
8. **Нищо, което иска съвсем нов браузър.** Приложението се отваря на чужди телефони,
   включително стари. `structuredClone` беше премахнат по тази причина (иска Safari 15.4+).
   Преди да добавиш ново API, провери дали го има в Safari отпреди поне три години.
9. **Никакви лични стойности по подразбиране.** Мерките в `DEFAULTS` са неутрални
   запълнители, които никой не вижда — истинските идват от първоначалния екран.
10. **Service worker-ът е „мрежа преди кеш“.** Не го обръщай на кеш преди мрежа заради
    скорост. Приложението се ползва от няколко души; при кеш преди мрежа разгърната
    поправка не стига до тях, докато не изчистят браузъра си. При всяка промяна на
    списъка `SHELL` вдигай и номера в `CACHE`.

## Работа с Claude API (vision)

Извикването е в `js/vision.js`. Два режима:

- `direct` — от браузъра към `api.anthropic.com` с хедър
  `anthropic-dangerous-direct-browser-access: true`. Ключът е на потребителя, в неговия
  браузър — приемливо за лично приложение, но ключът се вижда в DevTools.
- `proxy` — към Cloudflare Worker, който държи ключа като secret. По-чисто, ако линкът
  към приложението попадне у някого другиго.

Модел по подразбиране: `claude-sonnet-5`. Идентификаторите се пишат без дата:
`claude-sonnet-5`, `claude-opus-5`, `claude-haiku-4-5`.

Правила, които чупят заявката, ако се пренебрегнат:
- **Не задавай `temperature`, `top_p` или `top_k`.** На Sonnet 5 и Opus 5 тези параметри
  са премахнати и връщат 400.
- **Настройката за мислене зависи от модела.** Функцията `reasoning()` в `vision.js` я
  избира; не я заобикаляй с една обща стойност:

  | Модел | Какво се праща | Защо |
  |---|---|---|
  | `claude-sonnet-5` | `thinking: { type: "disabled" }` | Приема се. По-бързо и по-евтино. |
  | `claude-opus-5` | `thinking: { type: "adaptive" }` + `output_config: { effort: "low" }` | При изключено мислене Opus 5 изпуска `<thinking>` тагове в отговора и чупи JSON-а. Ниското ниво пази скоростта. |
  | `claude-haiku-4-5` | нищо | Не мисли по подразбиране и връща грешка при `output_config`. |

- Отговорът може да съдържа няколко блока. **Никога не чети `data.content[0].text`.**
  Филтрирай по `type === "text"` и конкатенирай.
- Тялото на отговора се разчита с `JSON.parse` в `try`. При грешно прокси се връща HTML,
  не JSON — потребителят трябва да види разбираемо съобщение, не `SyntaxError`.

Отговорът се иска като чист JSON. Моделът понякога го обгражда с ```json — `parseJson()`
чисти оградата преди `JSON.parse`. Резултатът винаги минава през екран за потвърждение;
нищо не влиза в дневника без потребителят да го е видял и да е могъл да го редактира.

Снимката се свива до 1280 px по дългата страна и се кодира като JPEG q=0.82 преди
изпращане — така една оценка струва под цент и се качва бързо по мобилни данни.

## Стил на кода

- Модули с именувани експорти. Без класове, без глобални променливи освен `S` в `state.js`.
- Функции по 30 реда максимум. Ако расте — разделяй.
- Български в интерфейса, английски в имената на променливи и в коментарите по код.
- Никакви `alert()` за нормални състояния — само `toast()` от `util.js`.
- Отказите и грешките казват какво се е случило и какво да направи потребителят.

## Локално стартиране

ES модулите изискват HTTP сървър (`file://` дава CORS грешка):

```bash
python3 -m http.server 8080
```

После `http://localhost:8080`. За тест на камерата от телефон трябва HTTPS — виж README.

## Какво да не правиш

- Да не добавяш анализ на теглото под формата на съвети за диета. Приложението показва
  числа; хранителният режим се води от нутриционист.
- Да не пращаш данни никъде освен към Claude API за оценка на снимката.
- Да не сменяш модела на по-евтин без да провериш качеството на оценките — разликата
  при разпознаване на порции е осезаема.
